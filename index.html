사내 AI 개발 플러그인 — Redmine 연동 기능 설계·구현

AI가 작성한 코드의 검증 단계 — 리뷰 스킬

AI가 기능 해석, 테스트, 코드를 모두 작성하면 테스트가 통과해도 스스로 맞다고 확인한 것에 가깝습니다. 그래서 완성된 코드를 별도로 다시 읽고 문제를 찾는 리뷰 스킬을 만들었습니다.

  • 검토 방식테스트는 통과하지만 동작이 틀린 경우, 테스트가 부족한 경우, 구조가 잘못된 경우를 찾는 데 집중합니다. 테스트 이름이 아니라 내용을 읽고, 해당 로직을 지우면 테스트가 실제로 실패하는지까지 확인합니다.
  • 기록 방식문제마다 번호·심각도·파일 위치(file:line)를 기록하고, 다시 실행해도 같은 결과가 나오게 했습니다. 사용자와 합의하기 전에는 코드를 고치지 않습니다.
  • 결과처음 설계해 만든 뒤 팀과 함께 보완해 왔고, 고객 프로젝트 5개 모두에 적용했습니다. 리뷰를 마친 작업 단위는 88건이고, 한 프로젝트에서는 결함 131건을 기록해 72건을 해결했습니다.

한국사 기출 RAG — 답변 품질 측정과 개선

혼자 진행 · 2026.10 ~ 진행 중

RAG로 기출문제를 푸는 시스템입니다. 정답률보다 "답의 근거를 실제 자료에서 댈 수 있는가"를 기준으로 삼았고, 제가 직접 원문을 읽고 채점한 결과로 개선 효과를 확인했습니다.

데이터 준비

  • 문서 추출·OCR기출 PDF 4회분 200문항을 AI 없이 글자 위치 정보로 추출하고, 글자 정보가 없는 스캔본은 macOS Vision OCR로 처리했습니다. 기존에 교정해 둔 1회분과 비교해 차이 0건이었고, 항목과 사건의 짝이 깨져 있던 연표 문항은 위치 정보로 구조를 복원했습니다.

측정 방법

  • 정답 데이터 구축인용한 자료가 답을 뒷받침하는지 뒷받침함 / 일부만 / 아님 / 인용 없음으로 판정하고, 기준은 문서로 정리해 애매한 경우가 나올 때마다 보완했습니다.
  • 우연 여부 확인같은 설정으로 한 번 더 실행해 보니, 해설 문장과 일부 인용(7/30)은 바뀌었지만 답과 근거 판단은 그대로였습니다. 그래서 해설이나 인용만 바뀐 경우는 개선으로 세지 않았습니다.
  • 새 문항으로 확인튜닝에 쓰지 않은 30문항을 뽑아 설정을 바꾸지 않고 한 번 실행했습니다.
  • 사람·AI 판정 비교같은 30문항을 모델도 1차로 판정하게 하고, 제 판정과 문항별로 비교했습니다. 일치율 86.7%(26/30)였고, 다른 4문항은 AI가 더 엄격한 경우 2건, 더 느슨한 경우 2건으로 한쪽으로 치우치지 않았습니다. 해설을 쓴 모델이 스스로 채점한 결과라 성능 수치로는 쓰지 않고, 제가 검토할 순서를 정하는 데 씁니다.
  • 정답 유출 방지기존 시스템이 프롬프트에 정답을 넣은 채 일치율 100%를 내던 것을 발견해, 정답이 섞이면 실행이 막히도록 고쳤습니다.

개선 전후 비교는 튜닝 문항 기준이며, 처음 보는 문항은 최종 설정으로만 측정했습니다. 정답률은 검색 없이도 99%여서 성과 지표로 쓰지 않았습니다.

  • 남은 문제근거가 일부만 있는데도 모델이 "충분"이라고 답한 경우가 5건 남았습니다. 다음 단계는 정답 보기의 내용이 원문에 모두 있을 때만 "충분"으로 보도록 기준을 엄격하게 하는 것입니다.

트러블슈팅 1 — 자동 지표 98%, 직접 확인 30%

  • 문제시스템은 "근거로 뒷받침됨 98%"를 보고했는데, 원문과 직접 대조해 보니 정답의 근거가 실제로 있는 문항은 30%(9/30)였습니다.
  • 원인자동 지표는 인용한 문서가 검색 결과 안에 있는지만 확인하고 있었습니다. 없는 문서를 지어내는 것은 잡지만, 그 문서에 정답 근거가 들어 있는지는 보지 않았습니다. 정답률도 기준으로 쓰기 어려웠습니다. 검색 없이 푼 경우 99.0%(198/200), 검색 자료를 준 경우 98.5%(197/200)로, 모델이 이미 알고 있는 지식으로 맞히고 있었습니다.
  • 해결기준을 근거 뒷받침률로 바꾸고, 원문과 대조한 정답 데이터(기준표·채점 시트)와 재채점 절차를 만들었습니다. 자동 판정은 참고용으로만 남겼습니다.
  • 결과30%라는 출발점이 정해져 이후 개선 효과를 비교할 수 있게 됐고, 세 번의 개선 후 처음 보는 30문항에서 80.0%가 됐습니다. 정답률만 봤다면 드러나지 않았을 문제입니다.

트러블슈팅 2 — "자료가 부족하다"는 판단이 틀렸던 경우

  • 문제두 번째 개선 후 남은 12문항은 처음에 "DB에 자료가 없어서"라고 판단했고, 자료를 더 모으는 것을 다음 작업으로 생각했습니다.
  • 원인자료를 추가하기 전에 필요한 용어 14개를 DB에서 직접 찾아보니 모두 있었습니다. 문제는 검색어였습니다. 문제가 묻는 대상으로만 검색했는데, 정답을 가르는 단서는 대부분 보기 문장에 있었고(12문항 중 10문항) 그 단어가 검색어에 들어간 적이 없었습니다.
  • 해결모델이 답을 고른 뒤 "대상 + 고른 보기 문장"으로 한 번 더 검색해 근거를 보충하는 단계를 넣었습니다. 틀린 보기에 끌려가지 않도록 고른 보기 하나만 검색했고, 고유명사는 벡터 검색보다 키워드 검색(BM25)이 잘 찾아서(한 사례에서 4위 vs 30위) BM25를 썼습니다. "옳지 않은 것" 유형은 문장의 실제 주어를 먼저 뽑아 검색어에 넣었습니다.
  • 결과근거 뒷받침률 60.0% → 93.3%(튜닝 문항), 처음 보는 30문항 80.0%. 자료는 한 건도 추가하지 않았습니다.
